# 项目总览：Lean 建模与 MAGMA 审计（截至 2026-11-28，第 82 轮）

图表见 `operators/magma/viz/overview.html`，由 `operators/magma/viz/make_overview.py` 从 FINDINGS.csv 和 Lean 文件统计生成。
机制分析和逐轮细节见 `BUG_DISTRIBUTION_zh.md`、`COVERAGE_zh.md`、`HANDOFF.md` 第 29 节。

## 1. 做了什么

研究目标是验证两类数值代码：
- AI 时代的低精度内核：要求便宜，且具备基本可靠性；
- 用低精度模拟高精度的内核：要求深入，且可靠性高。

从 2026-11-24 起，重点放在**混合精度迭代细化（IR）的接受逻辑**上，之后扩展为对 MAGMA 2.10.0 全库的审计。

方法分三层：
- **读码建模**：把代码里的判定逻辑、状态传递、尺寸算术写成 Lean 4 模型，并证明缺陷存在（一般形式加具体实例）。
- **GPU 差分测试**：在 roxy（Windows，RTX 级 GPU，CUDA 13）上对照 LAPACK 或按文档写的 CPU 参考实现。手段包括：
  - 工作区后面放保护区（哨兵）；
  - 不该读写的区域填 NaN 或哨兵；
  - 单卡模拟多卡，并加调度模糊；
  - 补丁验证：把修好的源文件链接在库前面。
- **记录**：每条缺陷进 `FINDINGS.csv`，每轮写 `TRIAGE.md`。

## 3. 找到了什么

`FINDINGS.csv` 共 289 条（M001–M290，M244 已撤回）：
- 229 条（79.2%）在 GPU 上实测复现，7 条在 CPU 上确认，4 条用单卡模拟多卡确认，35 条只读码，14 条未能复现；
- 256 条有对应的 Lean 定理；
- 后果为静默错误（返回成功但结果错）的有 150 条（51.9%）。

`findings_stats.py` 排除未复现的条目后按 275 条计，得到静默错误 52.7%、GPU 复现率 83.3%，与上面的口径不同。

**集中在哪里**（按子系统）：
- 混合精度 IR（43）、稀疏格式 / IO / 工具（39）、批量 / vbatched（34）三个子系统最多；
- 其后是稠密特征值（26）、稀疏求解器（24）、稀疏 BLAS（22）、magmablas 内核（21）。

总的规律是：越靠近组合层和接口层（格式转换、批量调度、驱动程序），缺陷密度越高；核心数值内核本身相对干净。

## 4. 反复出现的机制（每一种都对应一种机械化的检查方法）

1. **复制代码时没有随约定调整**：
   - LAPACK 的参数号、lda = n；
   - 复数版本漏了共轭（geam ConjTrans、Jacobi 转置、IDR 角度只用实部）；
   - 生产方和使用方的格式约定不一致（gehrd_m 与 unghr_m 的 T、COO 的 row/rowidx）。
2. **快速返回和小尺寸 / 边界分支**：k = 0、n = 1、空行、非 16 / 128 倍数的尾块。
3. **主机和设备两份副本不一致**：只出现在 CPU-GPU 混合算法里，例如 geqp3。
4. **状态在层与层之间丢失、覆盖或清零**；同一参数在两处计算、彼此不一致。
5. **工作区和尺寸算术**：文档给的大小不够（geqr2x 实际用到 50n）、32 位溢出。
6. **NaN / Inf 通过"比较为假"漏过检查**。
7. **编译配置和平台分支**：HIP、ILP64、Windows 上 long 是 32 位。
8. **写死的资源上限**：
   - 共享数组 `sum[128]` 被 k 个线程使用（geqr2x n ≥ 130）；
   - `<<<1, nrhs>>>` 在 nrhs > 1024 时启动失败（hetrs_gpu）；
   - gridDim.z 超过 65535。
9. **并发与内存模型**：跨 queue 交接、轮换缓冲区复用、warp 内无同步归约、主机缓冲区被提前改写。

## 5. 方法上的经验

- 测试程序自带的参考实现可能和被测代码犯同样的错误（geam），所以参考实现必须按文档独立写。
- 测试程序给工作区分配得比文档大，会掩盖越界写（M261、M274），所以工作区要按文档大小分配，后面再接保护区。
- 早期只测到某个尺寸上限的地方（例如 n ≤ 128），要回头检查代码里有没有写死的资源上限。
- 按文件名搜记录会漏掉按例程名登记的条目，写探针前两种都要搜。
- 单卡模拟多卡会因为共用拷贝引擎而掩盖竞争；可分页内存会掩盖"主机缓冲区被提前改写"，要改用锁页内存。
